# AI Node Generation Quality Bugfix Design

## Overview

The ContextGraph intelligence engine produces shallow, topic-label-style nodes and meaningless edges despite having the infrastructure for rich semantic output. The core issue is that node generation operates in isolation (one segment → one prompt → one node) without awareness of the surrounding graph, and edges are computed via pure vector similarity without semantic reasoning. This fix introduces **graph-aware node generation** where the model sees neighboring nodes when creating new ones, **LLM-powered semantic edges** with typed relationships, and a **Graph Synthesis Pass** that holistically reviews the local graph after every materialization — free to rename nodes, improve summaries, create/remove edges, and improve local coherence. The goal is not better individual nodes — it's for the entire graph to read like an externalized memory of how ideas evolved over time.

## Glossary

- **Bug_Condition (C)**: The condition that triggers low-quality output — materialization and edge creation produce shallow, transcript-like results instead of insight-driven knowledge graph entries
- **Property (P)**: The desired behavior — nodes capture insights/realizations with emotional depth, edges explain conceptual evolution with typed relationships, the graph as a whole reads as externalized memory
- **Preservation**: Existing segmentation, routing, confidence gating, extend-node logic, and pipeline flow that must remain unchanged
- **Graph-Aware Materialization**: Node generation that receives context about existing nearby nodes so it can intentionally differentiate and position this node's unique contribution
- **Graph Synthesis Pass**: A post-materialization LLM call that reviews the local subgraph (new node + neighbors) and freely improves it — renaming nodes, rewriting summaries, creating/removing edges — to produce the best possible representation of the conversation's evolution
- **Semantic Edge**: An edge with a meaningful `relationship_type` (verb phrase) and `explanation` (sentence) generated by LLM reasoning, not just embedding similarity
- **Benchmark Evaluation**: Scoring engine output against predefined expected nodes/edges using the rubric in `/benchmarks/`

## Bug Details

### Bug Condition

The bug manifests when the engine materializes nodes or computes edges. The materialization prompt asks for a "noun phrase" title and "what they discuss" summary — explicitly instructing the LLM to produce topic labels rather than synthesized insights. The edge computation uses pure cosine similarity with no LLM reasoning, producing edges with `relationship_type = "related"` and empty explanations.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type { materializedNode: Node, edges: Edge[] }
  OUTPUT: boolean
  
  RETURN (
    input.materializedNode.title IS topic_label_style
    OR input.materializedNode.summary IS message_replay_style
    OR ANY edge IN input.edges WHERE (
      edge.relationship_type == "related"
      AND edge.explanation == ""
    )
  )
  
  WHERE topic_label_style := matches pattern "Exploring X" | "Discussion about X" | generic_noun_phrase_without_insight
  WHERE message_replay_style := starts with "Discussion about" | "They talked about" | summarizes_messages_not_conclusions
END FUNCTION
```

### Examples

- **Defective title**: "Exploring the Decline of Art Since 2021" → **Expected**: "Searching for Art That Feels Exciting Again"
- **Defective summary**: "Discussion about how art has declined in quality since 2021" → **Expected**: "A realization that mainstream art since 2021 has lost its emotional charge, prompting a search for creative forms that still provoke genuine feeling"
- **Defective edge**: `{ relationship_type: "related", explanation: "" }` → **Expected**: `{ relationship_type: "led to exploration of", explanation: "Dissatisfaction with modern art naturally led to exploring a genre that still feels emotionally charged" }`
- **Defective segmentation**: One monolithic node for art→rock→persona arc → **Expected**: 2-3 nodes tracking the conceptual evolution

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Exchange-based incremental segmentation algorithm (boundary detection via user-message cosine similarity)
- Routing logic: extend_node, accumulate, new_candidate decisions
- Confidence computation and materialization threshold gating
- MIN_EVIDENCE_MESSAGES guardrail (4 messages minimum)
- MAX_AUTO_NODE_MESSAGES / MAX_AUTO_NODE_SEGMENTS block checks
- Stale candidate promotion logic
- Node embedding computation and storage
- Position computation and neighborhood assignment
- Engine state persistence (cursor, openSegment, totalRuns)

**Scope:**
All inputs that do NOT involve the materialization prompt text, edge relationship generation, or post-materialization quality review should be completely unaffected by this fix. This includes:
- Segment boundary detection thresholds and logic
- Candidate creation, accumulation, and blocking
- Confidence scoring formula (coherence, distinctiveness, recurrence, quality weights)
- Database schema and persistence layer (existing columns already support relationship_type and explanation)
- React Flow rendering of nodes and edges
- The overall pipeline orchestration flow in `runPipeline()`

## Hypothesized Root Cause

Based on the bug analysis, the root causes are:

1. **Shallow Materialization Prompt**: The current prompt explicitly asks for a "noun phrase" title and "what they discuss" summary. This instruction forces GPT-4o-mini to produce topic labels rather than synthesized insights. The LLM is doing exactly what it's told — the instructions are the bug.

2. **No Semantic Edge Reasoning**: `computeIncrementalEdges()` uses pure vector cosine similarity. It never asks an LLM _why_ two nodes are related or _how_ one idea led to another. The `relationship_type` and `explanation` columns exist in the database but are populated with "related" and "" respectively.

3. **No Quality Feedback Loop**: Once a node is materialized, its title and summary are never revisited. If the first-pass output is shallow, it stays shallow forever. There's no mechanism to review a node in the context of its neighbors and improve it.

4. **No Benchmark Validation**: There's no automated way to compare engine output against expected quality standards, so regressions and improvements go unmeasured.

## Correctness Properties

Property 1: Bug Condition - Insight-Driven Node Materialization

_For any_ conversation segment that is materialized into a node, the fixed `materializeToNode` function SHALL produce a title that captures the core insight, realization, or emotional theme (not a topic label) and a summary that articulates what was concluded or learned (not a replay of what was discussed). When evaluated against the benchmark rubric, titles SHALL score ≥3 on the "Title quality" dimension and summaries SHALL score ≥3 on the "Summary quality" dimension.

**Validates: Requirements 2.1, 2.2**

Property 2: Bug Condition - Semantic Edge Generation

_For any_ pair of nodes where an edge is created, the fixed edge generation SHALL produce a meaningful `relationship_type` (e.g., "led to exploration of", "evolved into", "emotionally connected to") and an `explanation` sentence describing why the two ideas are connected — not merely "related" with an empty explanation.

**Validates: Requirements 2.3, 2.5**

Property 3: Bug Condition - Graph Synthesis Pass

_For any_ newly materialized node, the Graph Synthesis Pass SHALL review the local subgraph (new node + nearest neighbors) and produce improvements that make the graph read like an externalized memory of how ideas evolved. The pass is free to rename nodes, improve summaries, create edges with meaningful relationship types, and remove meaningless edges. After the synthesis pass, the local subgraph SHALL score ≥3 on all benchmark rubric dimensions (title quality, summary quality, edge quality, recall test).

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5**

Property 4: Preservation - Pipeline Mechanics Unchanged

_For any_ input that exercises the segmentation, routing, confidence gating, or materialization threshold logic, the fixed code SHALL produce the same segmentation boundaries, routing decisions, confidence scores, and materialize/block decisions as the original code, preserving all pipeline mechanics.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7**

## Fix Implementation

### Changes Required

Assuming our root cause analysis is correct:

---

### Change 1: Graph-Aware Materialization Prompt

**File**: `src/lib/intelligence/engine.ts`
**Function**: `materializeToNode()`

**Current prompt** (the bug):
```
"Analyze these messages and return JSON: {"title":"<noun phrase, max 60 chars>","summary":"<what they discuss, max 200 chars>"}. Raw JSON only."
```

**New prompt** — insight synthesis with graph awareness:
```
You are synthesizing a knowledge graph node from a conversation segment. This node will represent what was REALIZED, LEARNED, or EMOTIONALLY UNDERSTOOD — not what was discussed.

EXISTING NEARBY NODES (for context — differentiate from these):
{neighborNodesContext}

CONVERSATION SEGMENT:
{formattedMessages}

Return JSON:
{
  "title": "<the core insight, realization, or emotional theme — max 80 chars — NOT a topic label>",
  "summary": "<what was concluded, learned, or understood — max 300 chars — answer 'What insight emerged?' not 'What was discussed?'>"
}

BAD titles (topic labels): "Exploring Rock Music", "Discussion About Art Decline"
GOOD titles (insights): "Searching for Art That Feels Exciting Again", "Rock as the Sound of Authentic Emotion"

BAD summaries: "They discussed how art has declined and talked about rock music"  
GOOD summaries: "A realization that mainstream art lost its emotional charge, leading to rock music as an art form that still provokes genuine feeling"
```

**Key changes:**
- Pass existing nearby node titles/summaries as context so the LLM differentiates
- Instruction focuses on insight/realization, not description
- Few-shot good/bad examples included
- Increased max_tokens to 300 for richer output
- max title length raised to 80 chars (insights need more room)

**How neighboring context is obtained:**
- Load the 3 most similar existing nodes (by embedding cosine similarity against the candidate embedding)
- Format as: `• "Node Title" — Node Summary` for each
- If no nodes exist yet, omit the section

---

### Change 2: LLM-Powered Semantic Edge Generation

**File**: `src/lib/intelligence/engine.ts` (new helper function)
**Function**: `generateSemanticEdge()` (new)

**Trigger**: After `computeIncrementalEdges()` identifies node pairs above the cosine threshold, each candidate pair is passed to this function.

**Prompt:**
```
Two nodes in a knowledge graph represent ideas from the same conversation.
Determine how they are conceptually related.

Node A: "{titleA}" — {summaryA}
Node B: "{titleB}" — {summaryB}

Return JSON:
{
  "relationship_type": "<verb phrase, e.g. 'led to exploration of', 'evolved into', 'emotionally connected to', 'inspired', 'contrasts with', 'became foundation for'>",
  "explanation": "<one sentence explaining the conceptual connection>",
  "direction": "a_to_b" | "b_to_a" | "bidirectional"
}
```

**Integration with existing pipeline:**
- `computeIncrementalEdges()` continues to identify candidate pairs by embedding similarity (unchanged)
- For each pair, call `generateSemanticEdge()` to get the relationship type and explanation
- Store in existing DB columns: `relationship_type`, `explanation`
- The `direction` field determines which node is source vs. target (currently arbitrary alphabetical ordering)

**Cost control**: Only generate semantic edges for NEW edges (not re-process existing ones). Limit to max 3 edge generation calls per engine run.

---

### Change 3: Graph Synthesis Pass

**File**: `src/lib/intelligence/engine.ts` (new function)
**Function**: `runGraphSynthesisPass()` (new)

**When it runs**: After every successful node materialization, as a final pipeline stage before persist.

**What it does**: Reviews the local subgraph (new node + its nearest neighbors) and asks:
> "If this were the best possible representation of how the user's ideas evolved, what would the graph look like?"

The LLM is FREE to:
- Rename nodes (improve shallow titles)
- Rewrite summaries (deepen insight capture)
- Suggest new edges with relationship types
- Suggest removing edges that don't add meaning
- Suggest merging nodes if they represent the same insight (emit as recommendation, not auto-merge)

**Prompt:**
```
You are reviewing a local section of a knowledge graph that represents how someone's ideas evolved during a conversation.

THE NEW NODE:
Title: "{newTitle}"
Summary: "{newSummary}"
Linked messages: {messageSnippets}

NEARBY EXISTING NODES:
{neighborsFormatted}

EXISTING EDGES IN THIS SUBGRAPH:
{edgesFormatted}

Review this subgraph. Your goal: make it read like an externalized memory — capturing what was learned, realized, and how ideas evolved.

Return JSON:
{
  "nodeImprovements": [
    { "nodeId": "...", "improvedTitle": "...", "improvedSummary": "..." }
  ],
  "newEdges": [
    { "sourceNodeId": "...", "targetNodeId": "...", "relationship_type": "...", "explanation": "..." }
  ],
  "removeEdges": ["edgeId1", ...],
  "notes": "brief explanation of changes"
}

Rules:
- Only improve nodes that are clearly shallow (topic labels, message replays)
- Only add edges that explain meaningful conceptual evolution
- Only remove edges that say nothing beyond "related"
- If everything looks good, return empty arrays
```

**Mutations emitted:**
- `update_node_content` (new mutation type): `{ nodeId, title, summary }`
- `add_edge` (existing): with semantic relationship_type and explanation
- `remove_edge` (existing): for edges the synthesis pass deems meaningless

**Scope limiting:**
- Only review the new node + up to 3 nearest neighbors
- Max 1 synthesis pass per engine run
- If the new node has no neighbors (first node in graph), skip synthesis pass

Add handler for `update_node_content`:
```typescript
case "update_node_content": {
  await db.from("nodes").update({
    title: m.title,
    summary: m.summary,

}
```

Update `add_edge` handler to write `relationship_type` (instead of hardcoded "related").

### Change 5: Benchmark Evaluation Utility

**File**: `src/lib/intelligence/benchmark.ts` (new)

A function that:
- Takes current graph state (nodes, edges) and a benchmark definition
- Scores each dimension 1-5 using the benchmark rubric
- Returns structured results

Can be called from a debug endpoint (`/api/debug/benchmark?id=...`) or from tests.

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, surface counterexamples that demonstrate the bug on unfixed code, then verify the fix works correctly and preserves existing behavior.

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix. Confirm or refute the root cause analysis. If we refute, we will need to re-hypothesize.

**Test Plan**: Run the engine on the art-rock-persona benchmark conversation and capture the materialized nodes and edges. Compare against expected output to quantify the quality gap.

**Test Cases**:
1. **Materialization Prompt Test**: Feed the art-rock benchmark messages to `materializeToNode()` and verify titles are topic-label style (will produce shallow output on unfixed code)
2. **Edge Generation Test**: Run `computeIncrementalEdges()` on benchmark nodes and verify edges have `relationship_type = "related"` and empty explanations (will confirm no semantic reasoning on unfixed code)
3. **Full Pipeline Test**: Run the complete pipeline on the benchmark conversation and score against the rubric (will score ≤2 on most dimensions on unfixed code)
4. **Segmentation Granularity Test**: Verify the art→rock→persona arc produces 1-2 oversized nodes rather than the expected 2-3 insight nodes (may fail on unfixed code)

**Expected Counterexamples**:
- Titles like "Exploring the Decline of Art Since 2021" instead of insight-driven titles
- Summaries that replay discussion content instead of articulating conclusions
- Edges with no relationship type or explanation
- Possible causes: prompt wording forces topic labels, no LLM in edge pipeline, no quality review step

### Fix Checking

**Goal**: Verify that for all inputs where the bug condition holds, the fixed function produces the expected behavior.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := materializeToNode_fixed(input)
  ASSERT result.title captures insight/realization (not topic label)
  ASSERT result.summary articulates conclusion (not message replay)
  
  edges := computeEdges_fixed(result.node, neighborNodes)
  ASSERT ALL edges have meaningful relationship_type != "related"
  ASSERT ALL edges have non-empty explanation
  
  qualityScore := evaluateAgainstBenchmark(result, benchmark)
  ASSERT qualityScore.titleQuality >= 3
  ASSERT qualityScore.summaryQuality >= 3
  ASSERT qualityScore.edgeQuality >= 3
END FOR
```

### Preservation Checking

**Goal**: Verify that for all inputs where the bug condition does NOT hold, the fixed function produces the same result as the original function.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  segmentation_original := checkSegmentBoundary(input)
  segmentation_fixed := checkSegmentBoundary_fixed(input)
  ASSERT segmentation_original == segmentation_fixed
  
  route_original := routeSegment(input)
  route_fixed := routeSegment_fixed(input)
  ASSERT route_original == route_fixed
  
  confidence_original := computeConfidence(candidate, nodes)
  confidence_fixed := computeConfidence_fixed(candidate, nodes)
  ASSERT confidence_original == confidence_fixed
  
  materialize_decision_original := shouldMaterialize(candidate, nodes)
  materialize_decision_fixed := shouldMaterialize_fixed(candidate, nodes)
  ASSERT materialize_decision_original == materialize_decision_fixed
END FOR
```

**Testing Approach**: Property-based testing is recommended for preservation checking because:
- It generates many random segment/candidate configurations to verify pipeline mechanics are unchanged
- It catches edge cases in threshold calculations that manual tests might miss
- It provides strong guarantees that segmentation, routing, and confidence logic are preserved

**Test Plan**: Observe behavior on UNFIXED code first for segmentation boundaries, routing decisions, and confidence calculations, then write property-based tests capturing that behavior.

**Test Cases**:
1. **Segmentation Preservation**: Generate random exchange embeddings and verify `checkSegmentBoundary()` produces identical shouldClose decisions before and after fix
2. **Routing Preservation**: Generate random segment+node+candidate configurations and verify routing decisions are identical
3. **Confidence Preservation**: Generate random candidate/node states and verify confidence scores are unchanged
4. **Materialization Threshold Preservation**: Verify `shouldMaterialize()` returns the same boolean for all candidate states
